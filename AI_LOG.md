## [2026-07-14] Milestone 0 smoke test — reasoning-model gotchas in llm.py
**Prompt/ask:** Run a live smoke test of `react_repro/llm.py::generate()` against z-ai/glm-5.2 via OpenRouter once the API key was filled in, to confirm the model responds and stop sequences are honored.
**Issue 1 — silent empty completions:** First call (`max_tokens=20`) returned `['']`. Raw API inspection showed `finish_reason: "length"` with `content: null` — z-ai/glm-5.2 is a reasoning model that spends its token budget on a hidden `reasoning` field before emitting `content`. At low max_tokens the reasoning phase alone exhausts the budget, so `content` never gets written.
**Fix 1:** Added `extra_body={"reasoning": {"enabled": False}}` to the OpenRouter request in `llm.py`. This suppresses the hidden CoT phase entirely — content now appears immediately (confirmed `finish_reason: stop`, `content: 'BANANA'`), and cost dropped ~19x (from $0.00044 to $0.000023 for the same prompt) since we don't pay for reasoning tokens we don't use. Also methodologically correct: ReAct/CoT already interleave explicit `Thought:` steps in the prompt, so a hidden reasoning phase on top is redundant and risks interfering with stop-sequence parsing of the `Action:`/`Observation:` structure.
**Issue 2 — n>1 silently ignored:** Requested `n=3` for CoT-SC-style majority-vote sampling; OpenRouter/provider (Decart) returned only 1 choice regardless of `n`, with no error — `len(response.choices) == 1` even when `n=3` was passed. This would have silently broken CoT-SC (majority vote over N samples degrades to a single sample, no error surfaced).
**Fix 2:** Rewrote `generate()` to never rely on server-side `n`. It now always requests `n=1` per call, and for `n>1` fans out `n` independent calls via a `ThreadPoolExecutor` and collects the individual results. Verified with `n=3` that 3 independent completions are returned (`count: 3`).
**Verification:** Re-ran three checks after both fixes — (1) basic short completion, (2) ReAct-style prompt with `\nObservation` stop sequence (truncation correct), (3) `n=3` sampling returning 3 independent completions. All passed.

# Assignment 3 — Paper Improvement (Confidence-Gated Adaptive Back-off)

## [2026-07-28] Entry-point selection — limitation analysis of Yao et al. section 3.3
**Prompt/ask:** Select one specific entry point in the ReAct paper to improve, per the Assignment 3 brief; raise max_tokens and sample size first since the n=10 gate trends were uninterpretable.
**Method:** Read the Assignment-2 n=10 trajectories programmatically rather than re-reading the report's conclusions, extracting per-episode action sequences and observation traces from `results/raw/*_n10.jsonl`.
**Finding that selected the entry point:** The paper's ReAct->CoT-SC hybrid backs off on exactly one condition — ReAct exhausted `max_steps` without emitting `Finish[...]`. In the FEVER trajectories, 8/10 episodes terminated at step 2 (one Search, immediate Finish), so that trigger fired on NONE of them; gold NOT ENOUGH INFO was predicted REFUTES 6/6 times. In HotpotQA, every *failing* episode instead burned all 7 steps (one reissued `Search[Hardley Flood]` verbatim). Conclusion: the paper's trigger detects *stuck*, and is structurally blind to *prematurely confident*. That asymmetry is the improvement's entry point.

## [2026-07-28] Pre-existing bugs found while reading the Assignment-2 code
**Issue 1 — `max_tokens=256` truncated completions.** Empty predictions (`''`) appear in `fever_cot_n10.jsonl`, `fever_cotsc_n10.jsonl`, `fever_standard_n10.jsonl`: the model was cut off before emitting `\nAnswer:`. Worse, `cot_sc()` drops empty strings from the majority vote, so truncation silently shrank the effective sample size rather than erroring.
**Fix 1:** `llm.DEFAULT_MAX_TOKENS` 256 -> 512, applied to baseline and improved arms alike so they stay comparable. Effect was large and is reported separately from the improvement's credit: FEVER Standard went 20% (n=10) -> 64% (n=100), FEVER ReAct 30% -> 72%. Most of the Assignment-2 "FEVER underperforms the paper" conclusion was this bug plus n=10 noise, not a real model-vs-PaLM gap.
**Issue 2 — no token accounting.** `response.usage` was discarded entirely, so the assignment's required accuracy-vs-computational-cost analysis had no data.
**Fix 2:** Added a thread-safe `TokenMeter` in `llm.py`; `run.py` snapshots it per question so every result record carries `prompt_tokens`/`completion_tokens`/`cost_usd`.
**Verification:** Re-ran the Milestone-0 smoke test after editing `llm.py` to confirm neither GLM-5.2 gotcha regressed — `reasoning: {enabled: False}` still yields non-empty content, and the manual n-way fanout still returns 3 independent samples for `n=3` (a server-side `n` would have returned 1).

## [2026-07-28] Implementation — react_repro/backoff.py
**Design:** Decomposed the single boolean trigger into three signals over a completed ReAct trajectory, each a callable registered in `TRIGGERS` so `run.py --trigger` selects an ablation arm. S1 `exhausted` = the paper's original condition (kept as the control, and as the default everywhere so unparametrized calls behave exactly as in Assignment 2). S2 `thin_evidence` = fewer than tau informative retrievals before Finish. S3 `unsupported` = a one-call verifier shown only the retrieved observations (deliberately not the model's own Thought steps, so it checks grounding rather than re-running the reasoning that produced the answer).
**Issue — entropy normalization was wrong, caught by a unit test.** `vote_entropy()` initially divided by `log(n_distinct)`, which rescales *any* uniform vote to exactly 1.0 — so a 2-way even split and a 10-way scatter scored identically, destroying the exact discrimination the signal exists to provide. The test `test_clean_split_below_scatter` failed and exposed it.
**Fix:** Normalize by `log(n_samples)` instead. 2-way split now 0.30 vs. 10-way scatter 1.0, so `TAU_ENTROPY=0.5` sits sensibly between them.
**Issue — a test made a live API call.** A composite-arm assertion invoked S3, which hits OpenRouter; unit tests must not depend on the network.
**Fix:** Assert against the `s2_thin_evidence` component directly. 37 tests pass with no network access.
**Concurrency:** `run.py --workers N` runs questions in parallel. Since each question constructs its own `WikiEnv`, the shared on-disk `wiki_cache.json` was open to interleaved read-modify-write corruption; added a module-level lock and one shared cache dict in `wiki_env.py` (which also lets workers reuse each other's fetched pages).

## [2026-07-28] Ablation scope cut by data — S2 does not work
**Method:** Ran plain ReAct at n=100 on both domains with `--diagnose`, which evaluates all three signals per question independently and scores each against the oracle "ReAct was actually wrong" label. Judged signals by *precision lift over the base error rate*, not raw fire rate — a signal can lift accuracy merely by firing constantly, which would degenerate the hybrid into plain CoT-SC and prove nothing.
**Finding:** S2 (`thin_evidence`) fails. On FEVER at tau=2 it fires 80/100 times at 30.0% precision against a 28% base rate = **1.07x lift** (essentially random). On HotpotQA it is *below* base rate (0.67x). Evidence *count* is not a proxy for evidence *quality*; many FEVER claims are genuinely single-hop and resolvable from one page. S3 (`unsupported`) works: 1.79x lift on FEVER, and S1|S3 reaches 86.4% precision on HotpotQA. S1 has 100% precision in both domains but only 1/100 recall on FEVER — confirming the blind spot quantitatively at scale.
**Action:** Dropped the S2-containing arms (`s1s2`, `cga`, `cga_tau1`) from the paid ablation and spent the budget on `paper` vs. `s1s3`. The S2 negative result is retained and reported — it is genuine evidence about *why* the paper's designers may have chosen a step-count trigger, and the tau sweep is reported from the free diagnostic pass rather than from paid arms.
